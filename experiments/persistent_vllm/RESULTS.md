# Persistent vLLM pilot

The currently running RL jobs were not changed. Their all-layer MLC-PPO first 10 updates averaged about 90.2 s/update, including roughly 7 s for a temporary FP32 actor snapshot and 16 s to initialize vLLM per update.

A vLLM 0.17.1 sleep-mode pilot on RTX A6000 / NVIDIA driver 535 failed while initializing the virtual-memory allocator with `CUDA Error: invalid argument`; this is not sufficient to establish the precise root cause. The alternative was to keep a smaller vLLM engine resident on the actor GPU without sleep mode.

PBS job 61546 loaded an FP32 actor and simulated FP32 Adam moment allocations, ran an 8-prompt short generation with a resident BF16 vLLM engine (`gpu_memory_utilization=0.20`), deliberately changed an actor matrix, wrote a checkpoint, reloaded it into vLLM, checked four values after BF16 conversion, and generated a second batch. Snapshot time was 9.24 s and vLLM's in-place reload time was 1.02 s. The probed changed weights exactly matched the actor's BF16 values. This tests a small subset of weights rather than all parameters. Free GPU memory was 29.73 GiB before the engine, 17.83 GiB with it resident, and 5.78 GiB after adding a synthetic 12-GiB activation allocation. The test temporarily enabled vLLM's pickle serialization to run the local probe callable; that setting was scoped to this pilot. It did not run PPO.

PBS job 61547 kept the 0.20-utilization vLLM engine resident while running one actual 28-head PPO update on the same 64 saved rollouts as the earlier matched benchmark. To fit it used microbatch 2, BF16 computation, FP32 master weights, gradient checkpointing, and response-length sorting. Trainer time was 44.81 s; the earlier trainer-only benchmark without a resident engine and with microbatch 4 took 40.99 s. Both used the same 49,988 valid rollout tokens; initial full-sequence PPO-ratio checks passed. PyTorch's reported trainer-only peak allocation was 33.47 GB and excludes the engine's allocation.

The snapshot, reload and training measurements came from separate jobs. A rough optimistic combination is 44.81 s trainer + 9.24 s snapshot + 1.02 s reload + approximately 15 s generation = approximately 70 s/update, versus approximately 90 s/update currently. This excludes control overhead and does not demonstrate a complete, synchronized multi-update system; production-length generation at 0.20 GPU utilization was not measured in the resident setup. It should not be represented as an observed end-to-end speedup. Additional tests are needed for 64-prompt capacity, long-running memory behavior, complete weight synchronization, checkpoint/resume, and behavior-policy mismatch.
